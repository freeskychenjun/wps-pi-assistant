# 代码审查与优化建议（2026-11-14，基于 v0.2.15）

> 审查范围：`bridge.js`（903 行）、`pi-assistant/js/taskpane.js`（3066 行）、`pi-doc-tools.js`、
> `install-addin.ps1` / `pack-release.ps1` / `start-bridge.*` / `watchdog.ps1` / `hidden-run.vbs`、
> `doc-assistant-prompt.md`、`README.md`、`.gitignore`、测试脚本。
> 行号以 v0.2.15（commit 38492ae）为准，后续改动请按符号名定位。

## 总体评价

工程质量整体较高，以下几处是明显亮点，重构时不要丢：

- **v0.2.3 大文档提速**：applyEdits「一次读全篇 → 本地定位 → 只对命中处取 Range」的思路正确，撤销走 WPS 原生拒绝修订 + 文本级兜底的双保险设计成熟；
- **自启链路**（S4U + wscript 窗口样式 0 + 看门狗）针对 Windows 11 控制台闪现的工程化处理非常细致；
- 三态徽标、诚实的 FAILED 提示、发布包自检、对外发布前的脱敏，都体现了「别静默失败」的正确取向。

问题集中在四类：**桥接服务的安全面**、**少量正确性 bug**、**逐段 COM 循环的性能税**、**taskpane.js 单文件的维护成本**。

## P0 · 安全（建议尽快修）

### 1. 桥接 HTTP 服务无鉴权 + CORS 全开 ⚠ 最高优先

位置：`bridge.js:599`、`bridge.js:614`

面板与桥接本就同源（都从 `http://127.0.0.1:3987/addin/` 加载），
`Access-Control-Allow-Origin: *` 完全没有必要，却把所有端点暴露给任意本机浏览器页面：

- `POST /prompt`（`bridge.js:804`）→ 以当前会话向 pi 发任意消息，
  而 pi 开着 `bash`（`bridge.js:29` 的 TOOL_ALLOW）＝**任意命令执行的 drive-by 入口**；
- `POST /docreq` 不带 `docKey` 时走 `turnDocKey || currentDocKey`（`bridge.js:233`）广播，
  面板 `serveDocReq`（`taskpane.js:1054`）只拦「有 docKey 且不等」，缺 docKey 的请求不设防
  → **可读取用户正在编辑的文档全文**；
- `/shutdown`、`/config`（含 API Key 落盘）同样裸奔。

修复组合（建议 ①+② 必做，③ 更彻底）：

1. 删掉两处 `Access-Control-Allow-Origin: *`（同源无需 CORS，EventSource 同源也不受影响）；
2. 校验 `Host` 头必须是 `127.0.0.1:3987`（防 DNS rebinding）；
3. 桥接启动时生成随机 token，`serveAddin` 输出面板 HTML 时注入，面板与
   pi-doc-tools（经环境变量传递）所有 POST 携带 `X-Bridge-Token`，桥接校验。

### 2. `doc_eval` 只读黑名单可绕过

位置：`taskpane.js:957`

现有正则拦 `TrackRevisions|\.Save(As)?\s*\(|\.Delete\s*\(|\.Paste|\.Copy\s*\(|FileCopy|WScript|Shell\s*\(|\.Add\s*\(`，但以下写入路径全部不在名单内：

- 属性赋值：`doc.Content.Text = "x"`；
- 插入类：`InsertBefore` / `InsertAfter` / `InsertParagraph` / `AddPicture`；
- 方括号属性访问：`doc["Content"].Text = "x"`。

建议：补充上述模式，并在代码注释与 README 中写明「黑名单只是护栏、不是安全边界」。

### 3. 静态目录前缀校验少一个分隔符

位置：`bridge.js:587`

`full.startsWith(ADDIN_DIR)` 会放行**同名前缀的同级目录**（如 `pi-assistant-xxx/`）。
一行修复：改为与 `ADDIN_DIR + path.sep` 比较。

### 4.（低优先）`bridge-config.json` 明文存 API Key

已文档化、已 gitignore，可接受；更稳妥的做法是 Windows DPAPI（`CryptProtectData`）加密落盘，
或只存 WPS PluginStorage + 环境变量。

## P1 · 稳定性 / 正确性 bug

### 5. `execSync("pi --list-models")` 阻塞事件循环最长 25 秒

位置：`bridge.js:490`

期间 SSE、`/health`、`/docreq`、`/prompt` 全部挂起——面板徽标闪红、agent 的 doc_read 直接撞
25 秒超时。改 `child_process.execFile` 异步 + 双层缓存（先回旧值，后台刷新完成后更新）。
`taskkill`（`bridge.js:265`）虽短暂也建议顺手异步化。

### 6. `dev_apply` 分支重复，第二个不可达（死代码）

位置：`taskpane.js:974` 与 `taskpane.js:1019`

974 行的版本（text 版）先 return，1019 行的（edits 数组 + 计时版）永远走不到，
且当前没有任何脚本在用后者（test-apply-perf.js 是本地 mock）。二选一删除，避免误导维护者。

### 7. 并发 prompt 无互斥

位置：`bridge.js:804`（/prompt 可重入）、`taskpane.js` sendMsg

`turnDocKey` / `fullText`（桥接）、`aiBuf`（面板）都是单值；流式期间再发一条会串话，
且 `message_start` 会清空 `fullText`（`bridge.js:368`）导致前一轮 done 文本残缺。

修复：桥接端 `/prompt` 加 busy 判断（返回 409 或排队）；面板端在收到 done/error 前禁用发送按钮。

### 8. 「撤销上轮」会连带拒绝用户的手工修订

位置：`taskpane.js:2536`（`while (curN > wantCount) Reject()`）

AI 这轮之后用户自己产生的修订（序号更高）会被一并拒绝。WPS 修订的 Author 与用户相同，无法按作者区分；
至少在撤销完成的提示语里写明「本轮之后的手工修订也会被回退」，
理想方案是快照时记录每条修订的时间戳，只拒绝区间时间内的。

### 9. 日志无限增长

`debug.log`（现 152KB，append-only）、`bridge.log`（`>>` 追加 + 看门狗每分钟可能写）、
`bridge-watchdog.log`、`tool-log.json`（每次全量重写、无上限）。

建议：加简单轮转——启动时/写入前检查 > 5MB 则 rename 成 `.1`（保留 1~2 份）。
debug.log 是排障命脉，别长到打不开。

### 10. 文档口径不一

README 第 11 行说 Node ≥18，`start-bridge.cmd` / `install-addin.ps1` 说 22+。统一为实测最低版本。

## P1/P2 · 性能

### 11. 逐段 COM 循环是面板最大的性能税（首选优化）

`Paragraphs.Item` 在 taskpane.js 出现 **24 处**，热点：

| 函数 | 现状 | 位置 |
|---|---|---|
| `buildParaTexts` | applyEdits/undo 用，4000 段 = 4000 次往返 | taskpane.js:1581 |
| `readParagraphs` | 逐段 `Range.Text` | taskpane.js:656 |
| `readOutline` | 逐段取 `Style.NameLocal` + `Range.Text` | taskpane.js:722 |
| `findText` | 逐段 `Range.Text` **叠加**每段一次 `Information(12)` | taskpane.js:865 |
| `readHighlights` | 逐段 + 部分高亮段逐词 `Words` | taskpane.js:761 |

统一方案：新增共享 helper——**一次 `doc.Content.Text`（1 次 COM）→ 本地按 `\r` 切分**得到全篇段落数组，
逐段 API 只在需要 Range/样式/信息位时用。防御：切分段数 ≠ `Paragraphs.Count` 时回退老路径（防 WPS 特殊文档）。

预期收益：doc_find 1.4s → 数十 ms；applyEdits/undo 的结构读取从「十几秒级」→ 1 次调用。

配套两个小改：

- `findText` 的表格判断改为「本地 indexOf 命中后，只对命中段查 `Information(12)`」；
- `readOutline` 若 `doc.Content.Text` 无标题样式信息需求，仍需逐段取 Style——可先本地筛掉空段再取。

### 12. `insertAfter` 后全篇重读，连续插入退化 O(n²)

位置：`taskpane.js:1541`（`pTexts = null`）

一条 insertAfter 就丢弃整个 pTexts，大文档连续插入 N 段 = N × 全篇重读。
改为局部失效：记录插入点之后的偏移增量，只修正受影响部分。
`applyParas`（taskpane.js:2198 附近）的连续 `InsertParagraphAfter` + 逐段取 Range 同理。

### 13. undo 的 Reject 循环 O(n²)

位置：`taskpane.js:2536`

每 Reject 一条就重数一次 `Revisions.Count`。改：拒绝固定次数（`to - from + 1`）后核对总数，
不符再走文本级兜底。

## P2 · 架构与可维护性

### 14. taskpane.js（3066 行）拆模块

无打包器依赖，`taskpane.html` 多个 `<script>` 顺序引入即可：

| 新文件 | 内容 |
|---|---|
| `js/md.js` | mdToHtml / mdInline / escHtml |
| `js/docread.js` | doc_* 读取、表格网格、cleanText、段落/表格索引 |
| `js/apply.js` | applyEdits/Comments/Rows/Images/Tables/Ops/Paras/Cells/HFs/Pages/Formats |
| `js/undo.js` | undoStack / beginTurn / endTurn / undoLastTurn |
| `js/chat.js` | SSE、消息渲染、斜杠命令、会话列表 |
| `js/taskpane.js` | onload 装配 + 全局错误上报（保留） |

### 15. 11 组 wps-* 块数据驱动化

现状是四张平行表：parseX × 11（taskpane.js:1429 起）、finishTurn 的 b 对象（taskpane.js:2954）、
stripBlocks 的 11 连环（taskpane.js:1318）、addBlockDisclosure 的 labels（taskpane.js:1445）。

改为一张注册表，全部从表生成，新增块类型只加一行：

```js
var BLOCKS = [
  { tag: "wps-edits",    key: "edits",    label: "修订",     apply: applyEdits },
  { tag: "wps-comments", key: "comments", label: "批注",     apply: applyComments },
  // ... 共 11 项
];
```

### 16. `parseBlock` 每种 tag 只取第一个块

位置：`taskpane.js:1418`

正则未加 `g` 标志：模型输出两个 `wps-edits` 块时第二个不执行、且原文泄漏进气泡。
改用全局匹配收集所有块再统一移除（`String.prototype.matchAll` + 逐个 replace）。

### 17. 工程化

- 根目录加 `package.json`（`private: true`），`npm test` 串起 test-apply-perf 等纯 mock 用例；
- 加 CI（GitHub Actions，windows-latest）：`node --check` 全部 JS + 跑 mock 测试，成本很低；
- 版本号收敛为单一来源：现在有三处（git tag、taskpane.html 的 meta ver、pack-release 默认值），
  建议 pack-release 从 package.json 读，meta ver 由打包时注入。

## P3 · 产品方向（可选）

### 18. 多文档并发

README 承认的最大功能短板。桥接的 per-docKey 路由（paneDocs / docReadPending / SSE 带 docKey）
已是现成骨架，下一步：**每个活跃 docKey 一个 pi 子进程**（spawn 参数同现有，session 按文档绑定），
SSE 事件分发逻辑不用改。注意限流（如最多 2 个活跃进程）防内存膨胀。

### 19. 上下文 token 膨胀

每轮 prompt 的「光标处摘要」全文进入用户消息 → 永久留在 pi 会话历史
（显示层 `historyFor` 已剥离【当前文档】段，但模型上下文里还在）。
若 pi rpc 支持 ephemeral/system 消息可解；不支持则在 system prompt 约定「摘要只对当前轮有效」。

### 20. 长任务时的工具刷屏

「⚙ 调用工具」每条一行 sys 消息，长任务（10+ 次工具）刷屏。
可改为计数徽标（「⚙ 已调用 12 次工具」+ 可展开明细），与 v0.2.6 的指令明细折叠风格一致。
